# บันทึกการตัดสินใจ

## D1: จะเก็บข้อมูลผู้ใช้ที่ Login ไว้ที่ไหน (ส่วนที่ 3)
- ทางเลือกที่คิดไว้: (A) React Context (B) Redux (C) ส่ง props ผ่านทุกหน้า
- เลือก: A — Context
- เพราะ: มีเพียง user และ token ที่หลายหน้าต้องใช้ และเปลี่ยนตอน Login/Logout จึงเหมาะกับ state ขนาดเล็กโดยไม่เพิ่ม dependency
- ข้อเสียของ A ที่ยอมรับ: ถ้า state ที่แชร์เพิ่มมาก การอัปเดต Context อาจ render หลาย component พร้อมกัน; ระบบตัวอย่างนี้มี state น้อยจึงยอมรับได้

## D2: จะจัดการสิทธิ์หน้าเว็บอย่างไร (ส่วนที่ 3)
- ทางเลือกที่คิดไว้: (A) ตรวจ role แยกในแต่ละหน้า (B) ใช้ Route Guard กลาง (C) ซ่อนปุ่มอย่างเดียว
- เลือก: B — Guard ตรวจ session และ role ก่อน render route
- เพราะ: เงื่อนไข redirect สำหรับไม่ Login และ role ผิดอยู่จุดเดียว อ่านและตรวจกรณีได้ครบ
- ข้อเสียของ B ที่ยอมรับ: Guard ฝั่ง browser ป้องกัน backend จริงไม่ได้; ในงานนี้เป็น Mock API จึงตรวจสิทธิ์ซ้ำในฟังก์ชัน mock ด้วย และระบบจริงต้องตรวจบน server

## D3: จะกำหนดความสัมพันธ์ของ Task กับ Project และผู้รับผิดชอบอย่างไร (ส่วนที่ 2)
- ทางเลือกที่คิดไว้: (A) เก็บชื่อ project และชื่อผู้รับผิดชอบซ้ำใน tasks (B) เก็บ `project_id` และ `assigned_to` เป็น foreign key (C) รวมทุกอย่างเป็น JSON
- เลือก: B — foreign key ไปยัง `projects` และ `users`
- เพราะ: ป้องกัน task อ้างถึง project/user ที่ไม่มีจริง และแก้ชื่อผู้ใช้หรือโครงการได้โดยไม่ต้องแก้ทุก task
- ข้อเสียของ B ที่ยอมรับ: query ที่แสดงชื่อจำเป็นต้อง JOIN และการลบข้อมูลต้องกำหนดนโยบาย FK

## D4: จะเปลี่ยนสถานะของ Employee ที่หน้าเว็บอย่างไร (ส่วนที่ 3)
- ทางเลือกที่คิดไว้: (A) เปลี่ยนหน้าจอก่อนแล้วค่อยบันทึก (B) รอ API สำเร็จก่อนค่อยเปลี่ยน (C) เปลี่ยนทันทีและคืนค่าเดิมเมื่อ error
- เลือก: C — optimistic update พร้อม rollback เมื่อ API ปฏิเสธ
- เพราะ: ผู้ใช้เห็นผลทันที ขณะเดียวกันหน้าจอจะกลับมาตรงกับ server เมื่อบันทึกไม่สำเร็จ
- ข้อเสียของ C ที่ยอมรับ: ต้องจัดการ rollback และกรณีคำขอซ้อน; ปุ่มของ Task ที่กำลังบันทึกจึงถูก disable

## D5: จะจัดเก็บ Mock Data และจำลอง API อย่างไร (ส่วนที่ 3)
- ทางเลือกที่คิดไว้: (A) ฝังข้อมูลใน component (B) แยกโมดูล mock API (C) เพิ่ม backend จริง
- เลือก: B — `src/mockApi.js` เก็บข้อมูลจำลองและคืน Promise ที่หน่วงเวลา
- เพราะ: แยกหน้าจอออกจากรายละเอียดข้อมูล และทำให้ loading/error มองเห็นได้โดยไม่ต้องติดตั้งฐานข้อมูลหรือ backend ซึ่งโจทย์ไม่ต้องการ
- ข้อเสียของ B ที่ยอมรับ: ข้อมูลอยู่ในหน่วยความจำและหายเมื่อ refresh; เหมาะกับการสาธิตเท่านั้น

## การใช้ AI
ใช้ AI ช่วยแยกข้อกำหนดโจทย์เป็นรายการตรวจสอบ และช่วยร่างโครงสร้างโค้ด/เอกสารกับตัวอย่างการแก้บั๊ก.
ผมจะทบทวนแต่ละส่วน อธิบายการตัดสินใจ และปรับแก้ได้ระหว่างการสัมภาษณ์.
